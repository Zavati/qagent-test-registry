# 08.1.7-C-FIX-2 — Extensão de cobertura para assertion STATUS ausente

## Fronteira

Correção do fluxo existente de `ASSERTION_COVERAGE_EXTENSION`: a ausência isolada de `STATUS` passa a produzir uma proposta **somente quando evidência de Learning sustenta a extensão**, em vez de exigir um gap adicional de tipo/paginação. Não altera o Test Design fonte, não injeta status na geração, não amplia admissão de mutations e não implementa D.

Caso de reprodução: `validar_estrutura_meta`, Test Design v7 `tdv_4599d10a-6598-4ae2-a580-3673ad83e3b5`, endpoint `cep_0e5a1c6088ab27464916698890389ef5a59c0472`. Assertions originais `JSON_PATH_EXISTS $.meta` e `SCHEMA csv_32471e6b793b1480a4f1c6ebe388d2caefd46ab8` permanecem intactas, na mesma ordem. O arquivo de fixture é uma cópia normalizada do Test Design fornecido; schemas/respostas de execução dos testes são sintéticos e não representam conteúdo real do schema referenciado.

## Política limitada

A nova proposta exige cenário NATIVE_V2/TEST_DESIGN_ONLY, categoria HAPPY_PATH ou SCHEMA_CONTRACT, GET/HEAD/OPTIONS, autenticação REQUIRED ou NONE, request/dados seguros, sem baseline protegida, sem intenção negativa e sem derivação já pendente. Exige pelo menos uma assertion SCHEMA com referência válida e todas as assertions anteriores efetivamente PASSED. A ausência de STATUS deve ser a única lacuna de cobertura reconhecida nesse novo caminho.

A evidência precisa corresponder a organização/projeto/endpoint/Test Design/versão/cenário/ambiente, com request materializada compatível, auth sanitizada comprovada quando requerida, resultados indexados compatíveis, resposta JSON utilizável e sem truncamento, redirecionamento ou erro. Aceita apenas status 2xx que possam sustentar a resposta de schema; 204, 205 e 206 ficam fora deste suporte. Não há default 200, união de códigos ou alteração de assertions já válidas. O código proposto é exatamente o código da execução aceita. Referências de grounding não substituem essa execução.

O veto conservador de intenção pode recusar texto ambíguo/negativo e status explícito conflitante no título/objetivo. Texto nunca escolhe o status. Não é um interpretador universal de linguagem natural. Suporte a tipo em arrays, status negativos sem assertion, ausência de schema, outras lacunas isoladas e mutations ficam fora do fix.

## Contratos e versões

O envelope existente `qagent.learning-coverage-proof.v1` ganha o campo opcional fechado:

```json
{"statusCoverageContractVersion":"qagent.status-coverage-extension.v1"}
```

Somente os novos proofs STATUS-only usam esse marcador. Incluem uma observação `kind=STATUS`, `actualStatusCode` e `schemaAssertionIndexes`, mais uma única adição `STATUS` com o código exato. Não contêm body HTTP, cookies ou valores de bindings. Não é campo para o navegador fabricar.

Proofs anteriores de tipo/paginação mantêm seu detector/shape original, inclusive STATUS como complemento. A aprovação recompõe o novo proof de fontes autoritativas e rejeita evidência mais recente diferente. O marcador persistido, não a flag atual, determina sua interpretação. Uma nova proposta marcada exige derivação C nativa pendente mesmo se a flag for desligada depois da criação.

O Registry valida esse marcador e exige `readinessReconciliationContractVersion=qagent.readiness-derivation.v1` no plano privado. A nova versão preserva assertions, request, autenticação, siblings e baseline e recebe `HYPOTHESIS/DERIVATION_PENDING_VERIFICATION`, `coverage=PARTIAL` e `ASSERTION_COVERAGE_VERIFICATION_REQUIRED`. Aprovação sozinha não promove regressão.

O rerun vinculado precisa comprovar todas as assertions, inclusive STATUS acrescentada. Após `COVERAGE_VERIFIED`, a projeção reconciliada pode produzir VERIFIED/COMPLETE/regression READY quando as demais condições forem atendidas. O JSON histórico não é regravado. Uma execução manual ou da versão fonte não substitui o vínculo de verificação.

## Publicação

Ordem: **Registry → Evolution → Gateway**. Manter ambas as flags atuais no Gateway/Evolution (`SCENARIO_READINESS_V2_ENABLED=true` e `SCENARIO_READINESS_RECONCILIATION_ENABLED=true`) para produzir propostas e usar a maturidade C. O Registry mantém a flag v2 do Explorer, mas valida os novos proofs independentemente da flag de leitura. Nenhuma migration/configuração/flag nova. Preservar bindings, secrets e configuração local; preferir overlay com checker.

Desligar C interrompe a produção do novo caminho. Propostas STATUS já registradas continuam sujeitas a sua semântica congelada, inclusive checagens estritas da verificação. Não voltar leitores/Registry/Evolution para binários anteriores com proofs marcados pendentes. O patch inverso desfaz arquivos, não converte registros. Não apagar versões/Results/recibos. O retry C-FIX-1 permanece intacto.

## Diagnóstico

`learning.coverageGaps` pode agora incluir `{ "kind":"STATUS", "code":"ASSERTION_STATUS_REQUIRED" }` quando o detector especializado não tem outro gap. Isso é diagnóstico, não autorização de proposta. `coverageStatus`, issues e admission continuam independentes. A projeção segura de `extension` no Analyze inclui marcador e observação sem valores privados.

Principais recusas: `LEARNING_STATUS_SCHEMA_REQUIRED`, `LEARNING_STATUS_INTENT_UNSUPPORTED`, `LEARNING_STATUS_OTHER_COVERAGE_REQUIRED`, `LEARNING_STATUS_RESPONSE_UNUSABLE`, `LEARNING_STATUS_ASSERTIONS_INCOMPLETE`, `LEARNING_STATUS_EVIDENCE_SCOPE_MISMATCH`, `LEARNING_STATUS_REQUEST_MISMATCH`, `LEARNING_STATUS_PROOF_INVALID`, `LEARNING_STATUS_DERIVATION_MARKER_REQUIRED`. Uma recusa exige conferir a evidência; não enfraquecer contrato para fazê-la passar.
