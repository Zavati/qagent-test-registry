# 08.1.7-C — Evidence Reconciliation & Maturity Promotion

## Escopo e estado
C implementada nesta árvore; teste local não equivale a deploy ou homologação. D não implementada. O refinamento do assessment que classificou um 401 esperado como suspeita de bug foi adiado pelo usuário e não foi alterado.

A base é Gateway B-FIX-1 + Evolution B + Registry B entregues nesta conversa. O fluxo principal B foi observado pelo usuário no ambiente (hipótese, aprovação, bloqueio de dados e mutation); o smoke B específico de cobertura PARTIAL ainda não foi demonstrado no ambiente. Ele permanece pendente, sem impedir esta implementação solicitada de C nem ser marcado como aprovado retroativamente.

## Snapshot versus maturidade efetiva
A versão persistida é imutável. Uma derivação real RESULT_EVOLUTION marcada C recebe snapshot NATIVE_V2, expectativa HYPOTHESIS/DERIVATION_PENDING_VERIFICATION e issue EXPECTATION_REVALIDATION_REQUIRED. Extensão de assertions também mantém ASSERTION_COVERAGE_VERIFICATION_REQUIRED e coverage PARTIAL até verificação. Não promove apenas porque foi aprovada.

O Run da versão fonte não verifica a versão derivada. Depois de nova execução compatível e verificação explícita da proposta, o ledger existente do Evolution sustenta uma projeção `evaluationScope=EVIDENCE_RECONCILED`, com expectativa VERIFIED, coverage COMPLETE e regressão READY, somente para a versão e o ambiente exatos. A specification persistida continua pendente; ela não é regravada para refletir o resultado posterior.

Uma execução compatível sem aprovação pode gerar EVIDENCED/COMPATIBLE_EXECUTION. Hipóteses continuam com EXPECTATION_APPROVAL_REQUIRED bloqueando regressão. Falha de assertion com evidência confiável produz CONTRADICTED/HUMAN_REQUIRED na projeção; erro de rede, auth inesperada, resposta truncada, request/versão/ambiente incompatíveis não ensinam uma expectativa nova. Nenhuma assertion é alterada para tornar uma falha verde.

## Responsabilidades
Gateway coordena a leitura autorizada, valida escopo/hash da projeção e usa uma cópia privada antes da seleção/materialização do Run. Os resolvers e guards atuais ainda são executados. O contrato wire do Runner não muda.

Evolution valida evidência do Results e recibo de verificação, usando o ledger existente e consultas limitadas. A reconciliação não chama IA, não cria proposta, não executa HTTP da aplicação nem escreve em Test Design/Results. As propostas de confirmação e extensão existentes são reutilizadas, sem um novo gerador universal de assertions.

Registry aceita o marcador interno congelado `readinessReconciliationContractVersion=qagent.readiness-derivation.v1` no plano de aprovação, valida proofs e cria o snapshot pendente somente na derivação real. Projeções EVIDENCE_RECONCILED são rejeitadas em persistência. O marcador não é um campo que o navegador pode fornecer como autoridade.

## Ativação
Publicar Registry compatível → Evolution → Gateway. Preservar seus bindings, secrets e configuração efetiva; os ZIPs não refletem necessariamente a configuração do deployment atual.

Gateway e Evolution exigem as duas flags:
```text
SCENARIO_READINESS_V2_ENABLED=true
SCENARIO_READINESS_RECONCILIATION_ENABLED=true
```
A flag nova vem false. A flag antiga também permanece no valor false dos arquivos-base: ao aplicar patches de configuração, integrar sua configuração true de A/B, não a sobrescrever inadvertidamente. Registry mantém a flag A do Explorer, mas não depende da flag C para validar marcadores/contratos.

## APIs de leitura
Reconciliação de uma versão (POST read-only, IDs apenas):
```http
POST /v1/console/projects/{projectId}/intelligence/test-readiness/reconciliation
Content-Type: application/json
```
```json
{"endpointId":"cep_example","testDesignVersionId":"tdv_example","environmentId":"env_example","scenarioIds":["test_001"]}
```
`scenarioIds` é opcional; máximo 50 selecionados. Não enviar readiness, resultados, maturidade, proof, auth ou payload de request nessa chamada.

Explorer existente com ambiente explícito:
```http
GET /v1/console/projects/{projectId}/intelligence/test-readiness/endpoints/{endpointId}/scenarios?testDesignVersionId={versionId}&environmentId={environmentId}
```
Mantém `readiness` histórico, acrescenta `snapshotReadinessV2`, apresenta a projeção efetiva em `readinessV2`, e acrescenta `effectiveReadiness`/`readinessReconciliation`. Sem ambiente ou com C desligada, conserva a leitura A/B. O resumo/inventário e a UI não foram convertidos para maturidade efetiva: isso não é D.

Preview paginado de projeto:
```http
GET /v1/console/projects/{projectId}/intelligence/test-readiness/reconciliation-preview?environmentId={environmentId}&limit=3
```
Máximo 10 endpoints por página. `summaryBasis=PAGE_ONLY_OVERLAPPING_DIMENSIONS`: totais da página, dimensões que podem se sobrepor; não são total global nem categorias mutuamente exclusivas. Seguir `page.nextCursor` quando disponível. Erros parciais retornam `complete=false`, nunca totals globais inventados. `executionStarted`, `appliedByThisOperation`, `versionsModified` e `aiCalled` permanecem false.

## Verification
Usar o fluxo existente de bounded rerun da proposta e sua rota `POST .../test-evolution/proposals/{proposalId}/verify-outcome`, com `rerunResultSetId` e `rerunRunId` do Run ligado à proposta. O Gateway existente valida a associação pelo idempotencyKey: um Run arbitrário não é automaticamente um bounded rerun. Não fabricar chaves nem usar a evidência da versão fonte. A C adequa o propósito do rerun pendente seguro para LEARNING; não adiciona autoaprovação ou disparo de Run pelas novas rotas de leitura. Políticas anteriores que já solicitam bounded rerun explicitamente continuam existentes, sem expansão nesta entrega.

## Limites e segurança
- C de maturidade cobre GET/HEAD/OPTIONS. Mutations e OBSERVED_BASELINE permanecem em seus caminhos protegidos, sem nova promoção C ou nova dependência no plano. Não ampliar Mutation Safety nem usar massa positiva para estabelecer intenção negativa.
- Evidência é confrontada com organization/project, endpoint, versão/número, cenário, ambiente, request/auth sanitizados e assertions indexadas. Controle determinístico é conservador: material incompleto pode impedir promoção.
- Um recibo continua útil após outro PASS compatível da mesma versão/ambiente; ele é revalidado, não copiado para outro cenário/versão. Evidência recente contraditória não é escondida por PASS anterior.
- Até 5 resultados de histórico por cenário, 12 leituras de detalhe por chamada e 50 propostas (com aviso de truncamento). Limites esgotados/indisponibilidade geram diagnóstico e complete=false. Materialização C segura falha fechado sem projeção completa; isso pode exigir ampliar diagnóstico em uma etapa futura, não forçar READY.
- Clone/request repair/designer não herdam maturidade por cópia. Os writers antigos continuam invalidando seletivamente snapshots; o adapter e a leitura C preservam pendência. Novo snapshot nativo C só nas derivações RESULT_EVOLUTION marcadas.
- Não há migration, backfill, novo serviço, novos providers, dependências, mudanças em Runner/Results/Orchestrator/Console ou refinamento do assessment IA.

## Rollback
Desligar a flag C no Gateway e no Evolution suspende os novos caminhos. Manter binaries compatíveis: versões C e planos de aprovação já persistidos contêm códigos/marcadores novos. Reverter para binários pré-C pode rejeitar essas versões. Retry usa o marcador já congelado, mesmo que a flag mude. Desligar a flag não apaga JSON, recibos ou histórico; tampouco reconverte snapshots C para A/B. Para recuperar artefato funcional anterior usar pinagem/histórico, não UPDATE manual no banco.
