# 08.1.7-A — Structured Readiness Foundation

## Scope and activation

Only phase A is implemented. `SCENARIO_READINESS_V2_ENABLED` defaults to `false` in both Workers. Set it to `true` in the Gateway and Registry runtime configuration to compute/persist new native generation snapshots and expose the additional detail projection. There is no tenant allowlist, migration, backfill, external service, new dependency or execution trigger.

`scenario.readinessV2` is the additive canonical snapshot. `automation.readiness` remains its legacy projection for new native generations. Old stored documents are not rewritten. Exact Test Design retrieval returns the stored artifact, not a mutated virtual document.

## Contract

- `qagent.scenario-readiness.v2`: `basis`, `evaluationScope`, `execution`, `expectation`, `coverage`, `review`, `regression`, `issues`.
- `qagent.readiness-issue.v1`: closed `code`, `kind`, `source`, `severity`, `blocksExecution`, `blocksRegression`, `humanRequired`, `resolution`, `contractVersion`.
- Schema files: `contracts/qagent.scenario-readiness.v2.schema.json` and `contracts/qagent.readiness-issue.v1.schema.json` (JSON Schema Draft 2020-12).
- `src/readiness/scenarioReadinessV2.js` validates cross-field coherence beyond JSON Schema: fixed safety flags, canonical/deduplicated issues, derived dimensions and native legacy projection.
- Issues contain no free text, selectors, payloads, credentials or response values. Human-facing explanations remain presentation.
- Present-but-invalid v2 is rejected; it never silently falls back to v1.

`basis=NATIVE_V2` identifies Gateway generation. `basis=LEGACY_PROJECTION` identifies the read-only adapter. `expectation.basis` is a separate field describing knowledge, such as `AI_ASSUMED`, `OBSERVED_EVIDENCE`, or `DERIVATION_PENDING_VERIFICATION`.

### Five dimensions

| Dimension | Meaning in A |
| --- | --- |
| execution | READY/BLOCKED from structured operational issues available in the Test Design. |
| expectation | HYPOTHESIS for ASSUMED; EVIDENCED from compatible generation evidence; UNKNOWN without enough support. |
| coverage | COMPLETE/PARTIAL/UNSUPPORTED from deterministic guard and existing assertion-capability diagnostics. |
| review | NONE/LEARNING_AVAILABLE/HUMAN_REQUIRED; LEARNING_AVAILABLE is a classification candidate, not admission. |
| regression | READY only with execution READY, EVIDENCED/VERIFIED expectation, COMPLETE coverage and no regression-blocking issue. |

VERIFIED, CONTRADICTED and PROPOSAL_AVAILABLE exist as reserved contract states. Phase A does not produce them from results or authorize them in a generation append. No evidence reconciliation, promotion or new proposal flow was introduced.

`evaluationScope=TEST_DESIGN_ONLY` is explicit. READY does not attest to a live target, a currently valid session, successful secret resolution, Mutation Safety authorization or completed runtime preparation. Those existing gates are still mandatory. Mutation-policy codes can represent a trusted issue, but A does not query or replace runtime mutation policy.

### Legacy projection for native generation

1. regression READY -> READY.
2. execution blocked by DATA_DEPENDENCY -> NEEDS_DATA.
3. otherwise blocked by AUTH_PROFILE_REQUIRED -> NEEDS_AUTH.
4. otherwise blocked by environment/runtime target -> NEEDS_ENVIRONMENT.
5. otherwise REVIEW_REQUIRED.

The derivation is deterministic. An AI-only `automationHints.reviewRequired=true` cannot block native readiness. AI hints may remain in existing bounded legacy blocker presentation; v2 classification never derives authority from those texts. The unchanged v1 Learning parser can still reject a candidate that v2 describes as LEARNING_AVAILABLE. Switching that parser/admission to v2 belongs to B.

## Producer boundary

Semantic Guard, Observed Auth Bridge and Test Data Planner expose `readinessIssuesByScenarioId` separately from AI model output. Semantic issues are collected BEFORE the old 40-item diagnostics cap. The planner's authoritative unresolved data supersedes provisional path/body requirements that it resolved. Existing secret sanitization, negative preparation, user-defined FIXED policy and baseline generation are preserved.

The builder attaches native v2 only after the existing sanitizer/guard/auth/planner chain and negative guard. Baseline composition also receives native v2 without modifying protected source, assertions, comparison policy, credentials or request references. Generated summaries reflect the new native legacy projection.

No browser/model-supplied readiness object is accepted as generation authority. Registry validates shape, code/flags, native projection and necessary structural consistency; it does not repeat all Gateway evidence semantics.

## Legacy adapter and immutable derivations

`src/readiness/legacyReadinessAdapter.js` is the only v2 classifier that interprets legacy blocker text, reusing the existing bounded parser. Unclassified reasons remain fail-closed. It uses grounding, request/auth/data structure, negative strategy, baseline protection and existing lifecycle/learning metadata.

A deliberate phase-A compatibility boundary: existing v1 derivation writers do NOT become an evidence-maturity engine. After existing proof/hash/approval checks, they remove stale v2 only from changed scenario copies. Unchanged siblings retain their native snapshot. Rename preserves v2 exactly. Clone does not inherit v2 or verified maturity. Parent JSON is never modified.

The read adapter uses existing immutable version-origin metadata for RESULT_EVOLUTION, HUMAN_REQUEST_REPAIR and SCENARIO_REQUEST_EDIT to conservatively project HYPOTHESIS / DERIVATION_PENDING_VERIFICATION for affected v1 scenarios. This is NOT confirmation/verification reconciliation. An old result cannot verify the new version. A legacy-derived item may retain persisted `readiness=READY` while its virtual v2 regression is BLOCKED; this mismatch is intentionally visible and does not change current execution policy. Rebuilding native maturity in those writers is deferred to the appropriate later phase.

## Read model

Gateway detail route:

```text
GET /v1/console/projects/{projectId}/intelligence/test-readiness/endpoints/{endpointId}/scenarios?testDesignVersionId={versionId}
```

Private Registry detail route:

```text
GET /v1/test-registry/projects/{projectId}/test-readiness/endpoints/{endpointId}/scenarios?testDesignVersionId={versionId}
```

`data.items[].readiness` stays the stored legacy label. When enabled, `data.items[].readinessV2` contains the native snapshot or the virtual legacy projection. Existing page/cursor/version and tenant boundaries remain. Project aggregates/filters are still v1: no v2 workspace or KPIs were added.

Legacy detail SQL extracts presence markers and classification metadata, not raw request bodies, credentials, generator configs or literal assertion values. Closed validators on BOTH sides reject unexpected fields. Reads never create versions or run tests.

## Rollout and rollback

Deploy the compatible Registry first, then Gateway through the existing deployment process. Both packages ship with the flag disabled. Enable both flags in a controlled environment and perform the stage-A smoke checklist. A stale Registry with its flag off will not provide v2 projections for new/old detail reads.

Disable the flag on Gateway to hide the new field and restore old generation behavior; disable it on Registry to stop producing virtual detail projections. Already persisted native JSON and its legacy projection remain immutable. A flag change is not a historical rewrite or automatic restoration of the previous version. Use the existing pinned-version/rollback process when the original artifact is required.
